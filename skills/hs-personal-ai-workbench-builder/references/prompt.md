# 个人AI工作台搭建流程 · 通用提示词文档

> 用途：不依赖任何 skill / 插件，把下面的提示词粘贴给任意 AI 编程助手
> （Claude / Cursor / Codex / Copilot / 通义 / DeepSeek 均可），从零搭一套
> 「本地运行、可手机访问」的个人工作台。
>
> **这份文档给的是推导方法，不是固定产品。**
> 模块怎么分、技术栈用什么、建几张表几个接口，都应该**从你的痛点推导出来**，
> 而不是照抄别人的模块清单。文档里出现的具体模块（每日必看 / AI 工具 / 素材区…）
> 只有两个作用：① 给你灵感和候选项；② 示范"痛点 → 模块 → 接口 → 表"的拆解手法，
> 你有新需求时照着这个手法推就行。
>
> 三个版本，按需取用：
> - **A. 极简版**（1 段话，快速起步）
> - **B. 完整版**（分阶段，推荐；含拆解方法、选型对照、接口推导）
> - **C. 增量版**（已有工作台，只加某块时用）
>
> 四个附录：模块灵感清单 · 完整拆解样例 · 技术栈对照表 · 高频坑速查表

---

## A. 极简版（复制这一段就能开工）

```
你是一名资深全栈工程师，帮我搭一个「本地个人工作台」，在我自己电脑上跑，
手机连同一 WiFi 也能打开。

但先别写代码，也别急着给我一套现成的模块清单。请按这个顺序来：

第一步，先跟我聊聊，不要问我"要哪些模块"。
我如果知道自己要哪些模块，就不需要你了。
请用开放式问题问我（一次问 1-2 个，等我回答再往下）：
- 你平时主要在忙什么？
- 每天有哪些事是你必须盯着、怕忘的？
- 有没有什么是你一直想记录、但没坚持下来的？为什么没坚持下来？
然后再问两个定架构的：
- 这个工作台主要在电脑上用，还是手机也要看？
- 里面会不会有你不想被别人看到的内容？

让我用大白话讲，你来负责翻译成模块。如果我答"你看着办"或说不清楚，
你就按常见场景先搭一版让我删，不要卡在原地反复问。

第二步，根据我讲的痛点，你来拆模块，然后列给我确认。
每个模块要说清楚：解决我哪句原话、数据从哪来、多久变一次、我是只看还是要改。
每条必须标类型：〔本地〕零门槛 / 〔内容〕一次性生成会过期 / 〔联网〕需要 key 可能挂。
联网型的必须当场告诉我代价和替代方案，不要藏到最后才说。
拆完主动告诉我哪些可以合并、哪些我可能没想到但值得加（最多推荐 2 个并说明原因）、
哪些建议先砍掉。
确认完模块清单后，**停下来等我说"可以了"再往下走**。

第三步，给它起个名字。会显示在标题栏和侧边栏顶上，
问我怎么叫它，不要替我拍板——这个名字我每天看好几次。

第四步，技术栈你给我 2-3 个方案对比，说明各自适合什么情况，
给出你的推荐和理由，**但最后让我拍板**，不要自己默认选一个就开写。

第五步，才开始写代码。每完成一块用无头浏览器截图自查，
零控制台报错才算通过，不要只跑 curl 就说"应该没问题"。

个性化信息（品牌名、路径、城市、账号等）一律放配置文件，不要硬编码。

最后给我一份《工作台配置.md》，记录模块清单和各自解决的痛点。
以后我想加功能时，读这份配置接着改，不用重新聊一遍。
```

## B. 完整版（分阶段，推荐）

### 阶段 0 · 开放式需求访谈（禁止跳过，禁止直接问模块）

```
在写任何代码、在提出任何模块方案之前，先跟我聊聊。

【重要】不要问我"你想要哪些模块"。
我如果知道自己要哪些模块，就不需要你了。请问痛点，模块由你来翻译。

请逐条问我（一次问 1-2 个，等我回答完再往下）：

【第 1 轮：三个开放式问题】
A. 你平时主要在忙什么？（工作、学习、带娃、做自媒体、备考、减肥……随便说）
   → 这一步定的是身份，决定后面推荐什么功能。答得太短就追一句具体在做哪方面。
B. 每天有哪些事是你必须盯着、怕忘的？
   → 挖的是高频刚需，这是工作台的骨架。
C. 有没有什么是你一直想记录、但没坚持下来的？为什么没坚持下来？
   → 答案往往是"要专门打开一个 App 太麻烦"，这正是工作台能解决的事。

【第 2 轮：两个定架构的问题（必须问，但像闲聊）】
D. 这个工作台主要在电脑上用，还是手机也要看？
E. 里面会不会有你不想被别人看到的内容？（日记、体重、账目……）

我回答时可能是很零散的大白话，不要要求我讲得结构化——
把零散的话整理成结构化需求是你的活，不是我的。

【如果我不配合】
- 我说"你看着办"/"随便" → 不要追问第二次。
  按常见场景先搭一版（计划+打卡+记账+设置），让我删。
- 连问两轮仍说不清 → 给最小四件套，说明先用起来就知道缺什么了。
- 我说的东西不像个人工作台（给团队用的、对外展示的）→ 直说这不合适，别硬套。

采集完，先用一句话复述你理解的"我最痛的三件事"，我确认后再进下一阶段。

> 📝 **产出《原始需求快照》**：访谈收口后，把我说的全部原话整理成一份快照存进项目
> （`docs/需求快照_YYYY-MM-DD.md` 或 README 的「原始需求」一节）。至少包含：Q1–Q5 的逐条
> 原话（用我自己的措辞，别急着翻译成模块）、复述确认过的"最痛三件事"、我明确说不想要的
> 东西。这份快照是以后复盘和加功能时的原始基准——几个月后你只会看到翻译后的模块表，
> 会忘掉我当时到底怎么说的。
```

### 阶段 1 · 归纳功能清单（由你产出方案，我来确认）

```
现在根据我讲的痛点拆模块。请用下面这套手法，不要凭感觉分。

【三层分类 — 每条必须标】
- 〔本地〕状态存本机，零门槛，不用解释
- 〔内容〕AI 一次性生成后写死，会过期，要告诉我大概够用多久
- 〔联网〕需要外部 API 和 key，可能挂掉
  → 联网型必须当场告诉我代价（要不要申请 key、大概多久）和替代方案
  → 绝对不要把联网型的代价藏到做完之后才说

判断方法：问自己"飞行模式下还能用吗"。能 → 本地或内容；不能 → 联网。

【拆解四问】每识别出一个候选模块，都要回答这四个问题：

1. 数据从哪来？
   - 外部接口（网上抓）→ 抓取型：要缓存、要容错、要显示更新时间
   - 本机文件/数据库（扫本地）→ 扫描型：要可配置根路径、要处理不存在的情况
   - 我手动录入 → 录入型：要建表、要增删改接口
   - 从其他模块的数据算出来 → 派生型：不要建新表，从明细现算

2. 多久变一次？
   秒级 / 分钟 / 小时 / 天 / 只在我操作时变
   → 直接决定缓存 TTL，以及要不要开预热线程。
     不变的东西每次都去抓是浪费；秒级的东西缓存久了就是错的。

3. 我是"看"还是"改"？
   只读 → 一个 GET 就够
   要改 → GET 列表 / POST 新增 / DELETE 删 / POST 切状态，四件套
   → 决定要不要建表、要不要写前端交互。

4. 没有数据时显示什么？
   → 每个模块都必须有明确的空态文案。
     没想好空态的模块，说明这个模块的价值你自己也没想清楚。

【模块的定义】
一个模块 = 一个痛点 + 一组同源数据 + 一个固定的查看动作。
三者缺一，它就不该是独立模块。

【合并判据】两个候选模块满足任一条，就合并成一个：
   - 它们回答的是同一个问题
   - 它们的数据来自同一个源
   - 我打开 A 的时候几乎总会顺手看 B

【粒度判据】
   - 一个模块应该能在一屏内看完；超过一屏，考虑拆
   - 一个模块少于三张卡片，考虑并进相邻模块
   - 侧栏一级入口控制在 3-6 个，超过我会找不到东西

【产出格式】按这个表列给我，等我确认：

| 模块名 | 解决我哪句原话 | 数据来源 | 变化频率 | 只读/可写 | 空态显示 |
|---|---|---|---|---|---|

列完这张表，还要主动告诉我三件事：
1. 哪两个我提的需求你合并了，为什么
2. 哪个模块你建议先砍掉（一期不做），为什么
3. 我没提到、但根据我的情况你觉得值得加的，是什么，为什么

如果我的痛点很少（只有一两条），就老实做小，
不要为了"看起来完整"硬凑模块。空页面比没有页面更让人烦躁。

【生成前最后一次确认】
列完模块表、我确认之后，再问一句：「还有别的想做进工作台的需求或痛点吗？」等我回答。
- 我答"还有"，就回到拆解环节，把新痛点也并进来重新确认。
- 我答"暂时没有 / 先把这些做扎实"，就**到此为止，只做确认过的模块**，
  不要替我猜测还有什么该加的。
这个确认是为了防止工作台从"每天真会开"变成"一堆从不点的死入口"。
这一步不能省，也不要把沉默当成"你帮我多想几个吧"。

> 🔴 **CHECKPOINT 1 · 功能清单**
> 我逐条确认之前，你不许进入下一步。我只回"嗯"不算通过——要追问一句。

【命名环节】
模块清单确认后，给它起个名字。
不要替我拍板——这个名字每天出现在标题栏和侧边栏顶上。
问我怎么叫它，给我 2-3 个候选让我挑（从我的话里取材）。
同时收齐个性化配置：品牌名/短名称(≤4字)/emoji/城市/路径/颜色偏好/标语。
这些全部进 config.json，代码里零硬编码。
```

### 阶段 2 · 技术栈选型（你负责介绍和推荐，我负责拍板）

```
模块定下来了，现在选技术栈。

【规则】不要直接开写。先给我一份选型对比，然后等我拍板。
你可以有明确倾向，也应该说出推荐和理由，但不要替我决定。

请按这个格式给我（每个方案都要说清代价，不要只说好处）：

| 方案 | 后端 | 前端 | 适合什么情况 | 代价 |
|---|---|---|---|---|

至少覆盖这几类，可以按我的实际情况增减：
- 零依赖单文件（如 Python 标准库 + 原生 JS）
- 轻框架（如 FastAPI / Flask / Express + 原生 JS 或 Alpine）
- 现代前端工程（如 Vite + React/Vue，配任意后端）
- 纯静态无后端（定时脚本生成 JSON，页面只读）

同时给我三个附属选择，同样是给选项 + 推荐，不要擅自决定：
- 数据存储：SQLite / JSON 文件 / 不持久化（每次重新抓）
- 如果模块里有隐私数据（日记、体重、账目、账号密码类）：额外给我一个加密存储的选项
  （如 SQLite 的 SQLCipher 静态加密，或 JSON 文件用 age/libsodium 加密），并说清代价
  （多一个依赖 / 要多记一个密码）。不要默认开，让我看到代价后自己决定；
  明文存密码这类东西绝对不行。
- 图表：成熟图表库 / 手写 SVG / 这版先不要图表
- 样式：手写 CSS / 原子化 CSS 框架 / 组件库

【选型时请按我的真实情况权衡，而不是按"什么最先进"】
重点问自己这几个问题，并把答案讲给我听：
- 我说过自己会不会改代码？不会改的话，越少文件越好。
- 我说过愿不愿意装环境？不愿意的话，直接排除需要构建步骤的方案。
- 这台机器要长期跑着吗？要的话，依赖越少越不容易某天突然跑不起来。
- 模块里有没有实时性要求高的？有的话再考虑轮询/推送，没有就别上。
- 未来三个月我大概率会往哪个方向加东西？别为想象中的需求提前上重型方案。

【默认倾向，仅供参考，我说了算】
个人自用、想随时手改、不想装环境 → 倾向零依赖方案：
单个后端文件 + 单个 HTML 文件，双击就能改，五年后还能跑。
但如果我的模块里有复杂交互（拖拽排序、富文本、多步表单），
就老实告诉我原生 JS 会写得很痛苦，该上框架就上框架。

我拍板之后，把选型结果和理由记进项目 README，
以后我回头看能想起当初为什么这么选。
```

### 阶段 3 · 接口与数据模型推导（从模块反推，不要照抄模板）

```
现在按我确认的模块清单，推导接口和数据表。
【重要】不要套用任何现成的接口清单。有几个模块就推几组接口，
我没要的模块，一个接口都不要留。

先遵守这套通用规范（这部分是死的）：

【命名】
- 路径统一 /api/<域>/<资源>，域名就用模块名，别自创缩写
- 可写资源四件套：
    GET    /api/<域>/<资源>            列表
    POST   /api/<域>/<资源>            新增
    DELETE /api/<域>/<资源>/<id>       删除
    POST   /api/<域>/<资源>/<id>/<动作> 状态变更
- 统计派生数据挂在 /api/<域>/<资源>/stats，不要单独建域

【返回体】
- 一律 {"ok": true, ...}，失败 {"ok": false, "error": "原因"}
- 抓取型接口必须带 fetched_at，前端要显示「更新 HH:MM」
- 任何一个外部源挂掉，只能让它自己那张卡片显示失败，
  绝不能让整页 500 或白屏

【一个看板一个接口】
如果某个模块里图表和列表展示的是同一批数据，
必须由同一个接口一次性返回，不要图表调 A、列表调 B。
两处数字对不上的时候，我会立刻不信任整个面板——
这是我踩过的坑，比多写一个接口的成本高得多。

【建表规则】
- 抓取型数据：不建表，走缓存
- 录入型数据：建表，必须有 id、created_at
- 派生统计：不建表，从明细表现算
- 计数器：单独一张表，初始值写 0（原因见阶段 7）

然后按上面的规范，为每个模块列出：
| 模块 | 接口 | 方法 | 说明 | 缓存TTL | 涉及的表 |
|---|---|---|---|---|---|

列完等我确认再写代码。
如果你发现某两个模块的接口高度重合，现在就提出来合并，
不要等写完了再返工。
```

### 阶段 4 · 项目骨架

```
按我选定的技术栈搭骨架，先跑通空壳再填内容。
下面以「零依赖方案」为例，如果我选了别的栈，你按等价原则调整，
但这几条通用要求不变：

- 端口从环境变量读，给个默认值
- 服务绑定 0.0.0.0（容器内，由平台映射端口）；对外访问地址是部署后的**稳定公网 URL**，不再是局域网地址
- 每个接口都包一层统一的异常兜底，内部抛错返回 {"ok":false,"error":...}
- 顶部主动清除 HTTP_PROXY / HTTPS_PROXY 等环境变量，
  否则本机请求会被系统代理拦截，表现是全部超时，很难排查
- 外部数据源用守护线程预热，让我第一次打开就有数据，而不是一片加载中
- 所有个性化信息进 config.json，代码里零硬编码；
  后端用 /api/config 暴露，前端启动时读取并注入标题和品牌名

零依赖方案的参考结构：

project/
├── server.py            # 全部后端
├── config.json          # 个性化配置（品牌/路径/城市/账号…）
├── data/app.db          # SQLite，首次运行自动建表
└── static/
    ├── index.html       # 全部前端
    ├── manifest.json    # PWA：名称/图标/全屏/启动屏
    ├── sw.js            # service worker：预缓存壳，离线可开
    └── <图表库>.min.js   # 本地副本，离线可用

部署阶段（见交付阶段）：用 Docker 打包（server + 前端 + 数据卷），数据通过挂载卷持久化到
宿主机本地；部署到稳定托管公网地址，链接不随沙箱休眠失效；PWA 让用户加到手机主屏幕、
离线打开、全屏无地址栏。数据始终本地保存，不迁云端。
```

### 阶段 5 · 前端结构

```
不管用什么框架，都要满足这几条：

- 左侧导航 + 右侧内容区；窄屏（<880px）侧栏收成汉堡抽屉，
  点导航项后抽屉自动收起
- 导航树、视图、数据加载三者用数据结构声明，不要散在各处硬写。
  原生 JS 的话，就是 TREE（导航定义）/ VIEWS{}（返回 HTML）/
  LOAD{}（异步加载）三张表 + 一个 renderView() 切换
- 统一的请求封装：失败返回 {ok:false} 而不是抛异常，
  避免一个接口挂了整个页面 JS 崩掉
- 写 innerHTML 前先判空，异步竞态时元素可能已经被换掉了

【默认落地页】
落在我每天真正要看的那个模块，不要做欢迎页/仪表盘首页。
第一屏必须已经有用，而不是让我再点一次才看到内容。
哪个模块当落地页，如果不确定就问我。

【合并优于加页】
如果两个页面在回答同一个问题，就合并成一个，不要各做一页。
这是我吃过亏的地方：曾经做了一个"总览页"又做了一个"明细页"，
两页显示互相重叠的数字，最后自己都分不清该看哪页。
每次你想新增一个页面时，先问一句：已有的页面能不能承载？

【删模块要删干净】
如果我砍掉某个模块，导航节点、视图函数、数据加载函数、后端接口、
相关表，五处一起删，不要留点了没反应的死入口。
```

### 阶段 6 · 视觉规范

```
主题风格听我的（先问我：暗色还是亮色？强调色偏好？），
但下面这几条是通用的，不管什么风格都适用：

- 阴影不要用纯黑，用带一点主色调的半透明色，纯黑阴影在深色背景上显脏
- 强调色通过 CSS 变量在运行时注入，方便一键换色，不要散落在各处写死
- 大面积纯色可以叠一层极淡噪点（SVG feTurbulence，透明度 0.03 左右，
  混合模式 overlay），能明显减少"塑料感"
- 栅格容器务必加 align-items:start——
  不加的话短卡片会被拉伸到和最高卡片一样高，页面全是空白
- 【标签化规则】一组名称（工具列表、标签、分类）要渲染成一个个圆角药丸，
  放在 flex-wrap 容器里，不要用逗号拼成一长串文本。
  20 个名字拼成的逗号字符串没人看得下去，20 个药丸一眼就扫完。
  超出数量显示「+N」
- 【卡片溢出规则】长 URL / 长路径在横向 flex 卡片里会把布局撑破。
  改成竖排（图标→名称→地址），并加 min-width:0 + overflow:hidden
  + word-break:break-all
- 每张数据卡片都要显示数据更新时间，让我一眼看出新不新
```

### 阶段 7 · 易错点（做到哪块看哪块）

```
下面这些不是通用规范，是具体功能的常见做错点。
只有当我的模块里真的包含这类功能时才适用：

【如果有"使用频率/次数统计"类功能】
1. 计数初始值写 0，不要写 1。
   写 1 的话所有条目看起来都"被用过一次"，图表变成一排等高柱子，
   毫无信息量。
2. 不要在请求路径里跑数据订正逻辑。
   我之前写过一个 UPDATE 把 hits=1 改成 0，结果它每次请求都执行，
   把真实点出来的计数全抹平了。这类订正只在"表里还全是初始数据"时跑一次。
3. 接口层过滤掉 0 值，并给一个明确空态文案，不要渲染一张全是 0 的图表。

【如果有"扫描本机文件/目录"类功能】
- 扫描根路径必须可配置，不要硬编码任何绝对路径
- 目录不存在时优雅降级，返回空列表 + 提示，不要抛异常
- 跳过以 _ 或 . 开头的目录
- 解析 YAML frontmatter 时注意块标量（|- 和 >-），
  简单按行 split 会把多行描述截断

【如果有"读取其他软件数据库"类功能】
- 一律以只读模式打开（如 sqlite 的 mode=ro），绝不写入别人的库
- 库文件不存在时返回 {"ok":true, "total":0, "error":"未找到"}，
  让前端显示空态，不要白屏
- 不要用扫系统进程的方式猜"什么程序在运行"。
  我踩过这个坑：ps 会把编辑器、Electron 外壳全算进去，噪音大到没法看，
  还得靠关键词硬猜。直接读目标软件自己的数据库，权威、廉价、准确。

【如果有"抓外部接口"类功能】
- 缓存命中时返回字典的新副本，并且首次抓取就把 fetched_at 写进去，
  否则命中缓存时前端拿到的时间戳是 null
- 国内不少接口是 GBK 编码，取文本要做 gbk 兜底解码
- 批量查询前先规范化每个参数，一个非法值会导致整批返回失败
```

## 附录 2 · 一个完整拆解样例（示范手法，不是让你照抄）

> 下面是一次真实拆解的全过程。看的是**推导链条**，不是最终模块。
> 你的痛点不同，推出来的模块就该不同。

**用户原话（零散的）：**
> "每天早上要开热榜、天气、股票三个页面…"
> "我装了一堆 AI 工具，但根本记不清自己装了什么"
> "我不知道我的 AI 现在到底在跑什么任务，有没有卡住"
> "想记每天干了啥，但记在备忘录里过两天就找不到了"

**第一步，套用拆解四问：**

| 原话 | 数据来源 | 频率 | 读/写 | 空态 |
|---|---|---|---|---|
| 热榜天气股票要开三个页面 | 外部接口 | 分钟~小时 | 只读 | "数据源暂时不可用" |
| 记不清装了什么工具 | 本机目录扫描 | 天（装了才变）| 只读 | "未扫描到工具，检查根目录配置" |
| 不知道 AI 在跑什么 | 本机软件数据库 | 秒~分钟 | 只读 | "未找到数据库" |
| 想记每天干了啥 | 手动录入 | 我操作时 | 可写 | "今天还没有记录" |

**第二步，应用合并判据：**
- 热榜 + 天气 + 股票 → 数据源不同，但**我每天早上是连着看的**，
  且都回答"今天外面什么情况" → **合并成一个模块**
- 工具清单 + AI 在跑什么 → 都回答"我的 AI 环境现在怎么样"，
  且都来自同一个本机根目录 → **合并成一个模块**
- 每日记录 → 独立诉求，独立模块（且它是唯一可写的）

**第三步，得出模块（从 4 条痛点收敛成 3 个模块）：**

| 模块 | 解决哪句原话 | 类型 | 落地页 |
|---|---|---|---|
| 每日必看 | 前两句 + 记录 | 抓取型 + 录入型 | ✅ 是 |
| AI 环境 | 中间两句 | 扫描型 | |
| （二期再说） | — | — | |

**第四步，反推接口（只推这三个模块要的，不多不少）：**

```
每日必看  GET  /api/daily/news      缓存 300s
          GET  /api/daily/weather   缓存 900s
          GET  /api/daily/stock     缓存 60s
          GET/POST      /api/daily/plan          录入型四件套
          DELETE        /api/daily/plan/<id>
          POST          /api/daily/plan/<id>/toggle
          GET           /api/daily/plan/stats    派生，不建表

AI 环境   GET  /api/aitools         扫描本机，缓存 600s
          GET  /api/ai/tasks        读软件数据库；图表和列表共用这一个
```

**第五步，注意这里做对的两个决定：**

1. **"AI 在跑什么"的图表和列表共用 `/api/ai/tasks` 一个接口。**
   最初版本图表调一个接口、列表调另一个，两处数字对不上，
   面板立刻失去可信度。合成一个返回体后问题消失：
   ```
   { ok, total,
     tasks:        [...],   // 列表用
     by_workspace: [...],   // 饼图用
     trend:        [...] }  // 折线用
   ```

2. **判断"什么任务在跑"，读软件自己的数据库，而不是扫系统进程。**
   最初用 ps 扫，把编辑器和 Electron 外壳全算进来了，
   只能靠关键词硬猜，噪音极大。改读数据库后，权威且零启发式。

**这个样例真正可复用的，是这五步推导，不是"每日必看/AI 环境"这两个名字。**

## 附录 2b · 复合模块「每日日常」拆解样例（示范合并手法）

> 当一组痛点都在回答"我今天过得怎么样"，它们不该拆成 4 个导航入口，
> 而是合成**一个落地页（复合模块）里的 4 个子模块**。下面是一套真实拆解。

**用户原话（零散的）：**
> "热榜、天气、股票三个页面每天早上一开就是三个"
> "早起、运动总坚持不下来，想一键打个卡看连续天数"
> "日程和待办散在备忘录，复盘也从不写"
> "钱花哪了完全没概念，想按月看看收支"
> "A股美股想放一块看，还想写两句盘面复盘"

**拆解四问（收敛成一个复合模块）：**

| 子模块 | 解决哪句原话 | 数据来源 | 频率 | 读/写 | 空态 |
|---|---|---|---|---|---|
| 每日资讯 | 热榜天气股票三页面 | 外部接口 | 分钟~小时 | 只读 | "数据源暂不可用" |
| 每日日程 | 打卡/日程/复盘 | 手动录入 | 我操作时 | 可写 | "今天还没打卡 / 暂无日程" |
| 记账记录 | 钱花哪了没概念 | 手动录入 | 我操作时 | 可写 | "本月还没有记录" |
| 每日股市 | A股美股想放一块 | 外部接口+录入 | 分钟+我操作时 | 读+写 | "行情加载中 / 还没写复盘" |

**关键决定：**
- 四个子模块都回答"今天的概览"，且几乎总是连着看 → 合成**一个落地页 `每日日常`**，
  导航只算 1 个入口，不是 4 个。
- 打卡用两张表：`checkin_items`（打卡项）+ `checkin_logs`（每天一条打卡记录）；
  "连续天数"由 `stats` 现算，不存字段。
- 记账的收支汇总、类目饼、余额趋势全部由 `ledger` 明细现算，不建统计表。
- 股市读 `config.json` 的 `markets`：每加一个市场（A股/美股/…）就多一列，
  不用改代码；批量查前必须 `normalize_code()`，一个坏代码会让新浪整批失败。

**反推接口（只推这个复合模块要的）：**

```
每日资讯   GET /api/daily/news       缓存 300s
          GET /api/daily/weather    缓存 900s
每日日程   GET/POST      /api/daily/checkin/items   录入四件套
          POST          /api/daily/checkin/logs     一键打卡(切换)
          GET           /api/daily/checkin/stats    现算连续天数
          GET/POST/DEL  /api/daily/events
          GET/POST      /api/daily/review
记账记录   GET/POST/DEL  /api/daily/ledger
          GET           /api/daily/ledger/stats?range=day|month|year
每日股市   GET           /api/daily/stock            markets 多市场
          GET/POST      /api/daily/stock/reviews
          GET/POST      /api/daily/stock/strategy
          GET/POST/DEL  /api/daily/watchlist
```

**这套真正可复用的，是"同类痛点合并成一个复合落地页"这个手法，不是"每日日常"这个名字。**
用户没有这些痛点时，一个子模块都不要硬塞进去。

| 方案 | 后端 | 前端 | 适合 | 代价 |
|---|---|---|---|---|
| 零依赖单文件 | 语言标准库自带 HTTP 服务 | 单个 HTML + 原生 JS | 个人自用、想随时手改、不装环境、要长期稳定 | 复杂交互写起来累；没有生态组件 |
| 轻框架 | FastAPI / Flask / Express | 原生 JS 或 Alpine | 接口较多、要自动文档、要异步 | 需要装依赖；环境可能随版本漂移 |
| 现代前端 | 任意 | Vite + React / Vue | 交互复杂、组件复用多、可能多人协作 | 需要构建步骤；改一行要重新构建；依赖树重 |
| 纯静态无后端 | 定时脚本产出 JSON | 静态页面读 JSON | 纯只读看板、想托管到静态空间 | 不能在页面上做任何写操作 |

**附属选择**

| 维度 | 选项 | 怎么选 |
|---|---|---|
| 存储 | SQLite / JSON 文件 / 不持久化 | 有可写模块就 SQLite；只有几条配置用 JSON；纯抓取展示就不存 |
| 图表 | 成熟图表库 / 手写 SVG / 不要图表 | 超过两种图表类型就上库；只有一两个进度条手写更轻 |
| 样式 | 手写 CSS / 原子化框架 / 组件库 | 单文件方案配手写 CSS 最省事；上了框架再考虑组件库 |
| 图表库引入 | CDN / 本地副本 | 想离线可用就存本地副本，并保留 CDN 兜底 |

## 附录 4 · 高频坑速查表

| 现象 | 根因 | 处理 |
|---|---|---|
| 本机请求全部超时 | 系统代理变量拦截 | 服务启动时清空 `HTTP_PROXY` 等 |
| 手机打不开 / 地址变了 | 用了局域网或隧道，没用稳定公网地址 | 改用 Docker + 稳定托管公网 URL，链接不随沙箱休眠失效 |
| 离线打开白屏 / 装不到主屏 | PWA 未配或 manifest 无效 | 校验 manifest.json + sw.js 同源可访问，display:standalone，图标多尺寸 |
| 接口整批返回失败 | 一个非法参数污染批次 | 请求前规范化每个参数 |
| 中文乱码 | 接口是 GBK 编码 | 取文本时加 gbk 兜底解码 |
| 数据时间戳是 null | 缓存命中时未带时间 | 首次抓取就写入，命中返回新副本 |
| 页面全是空白间隙 | 栅格拉伸短卡片 | 容器加 `align-items:start` |
| 卡片被长链接撑破 | 横向 flex 不换行 | 改竖排 + `min-width:0` + `break-all` |
| 图表是一排等高柱子 | 计数初始值写了 1 | 初始值写 0，接口过滤 0 值 |
| 用户点击的计数被清零 | 订正逻辑跑在请求路径里 | 只在全为初始数据时跑一次 |
| 进程列表里全是编辑器 | 用 ps 猜运行中的任务 | 改读目标软件自己的数据库 |
| 截图里图表显示"生成中" | 拍得太早 | 截图前等 2 秒以上 |
| 两处数字对不上 | 图表和列表用了不同接口 | 合并成一个接口一次返回 |
| 侧栏点了没反应 | 删模块时只删了导航 | 导航/视图/加载/接口/表 五处同删 |
| frontmatter 描述被截断 | 没处理 YAML 块标量 | 解析时支持 `|-` 和 `>-` |

## 附录 5 · 给 AI 的元规则（可附在任意提示词后面）

```
协作规则：
1. 需求先于方案。我描述痛点时，不要立刻给我一套模块清单，
   先确认你理解对了，再给方案。

2. 选项优于默认。技术栈、存储、图表库这类决策，
   给我 2-3 个选项 + 你的推荐 + 各自代价，让我拍板。
   你可以有倾向，但不要替我决定。

3. 不确定就去验证，不要用"应该没问题"敷衍。
   UI 相关的结论必须有截图支撑。

4. 我指出一个 bug 时，请修根因、改公共模式，
   让这类问题不会再出现在别处，而不是只补我指出的那一处。

5. 能合并就不要新增。新页面、新接口、新配置项都要先问一句：
   已有的东西能不能承载？

6. 涉及我的个人信息（品牌名、路径、城市、账号）一律走配置文件，
   不要硬编码进代码——这样我换个身份复用时不用改代码。

7. 做模板/分发版时，方向是单向的：
   我的实例 →（复制 + 清洗）→ 模板。
   永远不要反过来把我正在用的实例改成通用版。

8. 参考资料只是灵感来源。任何现成的模块清单、接口清单、表结构，
   都要先对照我的实际需求筛一遍，不要整套照搬。
   照搬来的东西我用不上，只会变成永远不点的死入口。
```
